# c2 — finding the optimum without searching the space

Contribution 2 of 4. Values in `paper/data/c2_*.json`; figures from
`paper/visualization/fig_c2_*.py` (unified style, single column 1.5:1,
multi column 3:1). Full protocol + gates: `research/94_composition/README.md`.

## design

**Claim.** Given a new (model, hardware, regime), a bounded measurement
budget finds a configuration within a few percent of the exhaustive
optimum over the COMPOSED lever space — and no proxy-scoring shortcut
can replace those measurements.

The negative half was settled earlier (phase 90): five proxy classes
falsified, so acceptance cannot be predicted, only measured. C2
supplies the positive half — a search with a MEASURED regret-vs-budget
curve against an exhaustive oracle.

**Why composition is the body.** Single levers (~13/arch) are
brute-forceable; C1 did exactly that. Composed, the space is
5 quant x 5 window x 3 skip x 2 kvq x 4 K x ~2 kernels ~ 1400 configs
per cell, ~30k per architecture column. Exhaustive is impossible, so
search becomes the contribution rather than a convenience.

**The factorization (the key structural claim).** The three quantities
behave differently and are separated accordingly:

| stage | quantity | depends on | how obtained |
|---|---|---|---|
| A | cost R | cell (batch x ctx) — measured CV 14.5% across cells, so NOT profilable | measure for singles per cell; predict compositions additively |
| B | acceptance p_i per depth | regime only — measured CV 2.2-3.3% across cells | measurement-only (phase-90 theorem); predict compositions from singles; confirm finalists |
| C | K and the final pick | neither — derived | argmax_K tau(K)/(K R(K)+1) in closed form |

K separates cleanly because with a SCALAR f, dS/dK = (f-R)/(KR+1)^2 is
sign-constant — K would always be K_max or OFF, contradicting every
measured cell. Acceptance decays with depth (measured -1.8% for
win8192 to -40.9% for win128 from K2->K6), and that decay is what
creates the interior optimum. One profile at K_max reconstructs tau(K)
for all smaller K (verified: 0.00% reconstruction error).

## evaluation

Oracle: exhaustive factorial over a reduced but COMPLETE space —
quant{none,q1,q2} x window{none,512,2048} x skip{none,b2} x K{2,4} =
36 boots per architecture, each covering the 9-cell batch x ctx grid.
Complete on dense-8B (36/36) and Llama-3.1-8B (36/36). Regret is
measured against the true optimum within that space; the deployable
space is ~40x larger and is addressed by the scaling claim, not by
this oracle.

### headline values

**The candidate set is singles UNION compositions** -- the search picks
whichever wins, and a single legitimately wins some cells (llama
b1/2k). C2 is not a claim that one should always compose; it is a
claim about finding the best member of the joint space.

**Composition beats the best single lever where the cost model says
it should** (dense 8/8 cells, llama 7/8):

| arch | cells >= +5% | peak gain |
|---|---|---|
| dense-8B | **6/8** | **+31.1%** (b8/14k: 1.24 -> 1.63) |
| Llama-3.1-8B | 4/8 | +17.5% (b8/8k: 1.12 -> 1.31) |

Gain is CELL-STRUCTURED: mean +8.1% at 14k ctx and +8.5% at b8, but
-2.0% at 2k and -0.0% at b1. Composition pays only where TWO cost
terms bind simultaneously (long ctx -> KV term, mid-batch -> weight
term); where one lever already removes the single binding term, the
second is pure overhead. At dense b32/2k composition also RESCUES a
cell where the best single loses to AR (0.97 -> 1.05 on llama).

**The search finds it cheaply.**

| method | dense mean regret | llama mean regret |
|---|---|---|
| best-single-only (the C1 policy) | 10.84% | 7.06% |
| search, confirm top-1 | 4.51% | 2.71% |
| search, confirm top-5 | **0.46%** | **0.00%** |
| random @ equal budget | 6.4-19.5% | 11.9-26.4% |

**The efficiency claim, stated as what is actually demonstrated:**
> search cost is O(#levers + #confirmations), INDEPENDENT of
> #compositions.

5 single profiles + N confirmations, and that count does not grow with
the composition count. On the 18-config oracle that is 16-22 of 36
boots (44-61%) — the reduced space is too small to show the saving.
Extrapolated to the deployable space (~16 singles, ~1384
compositions): ~21 boots, **~1.5% of exhaustive**. Direct
demonstration on the full space is Step 3.


### competing selection rules, scored against the same oracle

Every rule sees the same measured single-lever data and must choose a
composed config per cell; all are scored by the TRUE speedup of what
they chose. Pure analysis, no extra GPU.

| rule | dense (confirm 1 / 5) | llama (confirm 1 / 5) |
|---|---|---|
| best-single-only (C1 policy) | 10.84% | 7.06% |
| **ours** (additive R + kappa-corrected product, LCB rank) | 4.05% / **0.46%** | 2.39% / **0.00%** |
| product-of-singles (no correction) | 4.70% / 1.21% | 3.14% / 0.21% |
| KnapSpec-style knapsack (additive value/cost) | 4.41% / 1.77% | **1.37%** / 0.35% |
| proxy ranking (structural, no measurement) | **31.56% / 24.63%** | **24.28% / 14.60%** |
| random (5 draws) | 7.16% | 8.55% |

**The decisive result is not which aggregation rule wins -- it is that
INPUTS decide, not aggregation.** Proxy-ranked selection is
catastrophic (24-32% regret, never once picking the true best), while
three different aggregation rules fed MEASURED single-lever data all
land within 1.4-4.7%. This is the phase-90 measurement theorem
reproduced at composition scale, and it sharpens the KnapSpec
comparison: their published method pairs an additive knapsack with
COSINE-PROXY inputs; the knapsack aggregation is fine (1.4-4.4% here),
it is the proxy inputs that fail (24-32%). Our advantage over their
aggregation is real but modest (0.46 vs 1.77 on dense at confirm-5,
0.00 vs 0.35 on llama) and comes from the interaction correction.

**P5 RESOLVED -- and it under-stated the effect.** Registered as
"product-of-singles mis-ranks the top config at >=30% of cells";
measured top-1 mis-rank rates:

| rule | dense | llama |
|---|---|---|
| ours | 75% | 62% |
| product-of-singles | 100% | 62% |
| KnapSpec-style | 88% | 38% |
| proxy | 100% | 100% |

**CONFIRMED, far beyond the threshold** -- but note it applies to
EVERY rule including ours (62-75%). No ranking rule reliably picks the
exact winner first; that is precisely why the search confirms a
shortlist rather than trusting its own top pick, and why regret falls
to 0.00-0.46% at confirm-5 while top-1 accuracy stays low. Ranking
gets you into the right neighbourhood; only measurement closes it.



### mechanism: WHY composition wins or loses (term decomposition)

Decomposing S = tau / (K R + 1) for adding win512 to the quant single
(K=2; full table in `data/c2_decomposition.json`):

| cell | d(tau) acceptance | d(R) cost | d(S) result |
|---|---|---|---|
| llama b1/2k | **+0.0%** | **+0.5%** | -0.3% |
| dense b8/2k | -1.3% | -4.4% | +1.4% |
| dense b8/8k | -5.2% | -23.5% | +10.9% |
| llama b32/8k | -4.8% | **-48.4%** | +40.8% |
| dense b8/14k | -0.1% | **-49.8%** | +45.2% |
| dense b32/8k | -3.1% | **-57.6%** | **+55.3%** |

**Composition does not fail at b1/2k because acceptance drops -- tau is
literally unchanged (2.857 -> 2.857).** It fails because the second
lever has nothing left to cut: R moves +0.5%, i.e. very slightly
WORSE. At batch 1 x 2k the KV footprint is ~2k tokens, a negligible
share of the draft's cost, so windowing it saves nothing while the
scratchpad-gather machinery adds a small fixed overhead.

The general law, visible across every cell: **the acceptance cost of
composing is small and roughly constant (0-8%), while the cost benefit
ranges from nothing (+0.5%) to -58%.** Composition value is therefore
decided almost entirely by the DENOMINATOR -- by whether the added
lever's cost term is actually binding -- not by acceptance
degradation. This is the two-binding-terms law confirmed at the level
of the underlying terms rather than inferred from outcomes, and it is
what Stage-0 cell gating keys on.

### the b1/8k anomaly, RESOLVED: a single-document content draw

b1/8k appeared to break the pattern on BOTH architectures -- tau fell
21-24% there versus 3-8% at b1/14k. It is not a context-length effect
and not a property of composing. It is a sampling artifact, and the
resolution changes the verdict at that cell.

Three measurements settle it (data: `paper/data/c2_b1_8k_anomaly.json`,
figure: `paper/figures/content_variance.pdf`):

1. **A fine context sweep is jagged, not monotone.** Holding the stack
   fixed and sweeping ctx over 9 values, win512 dips at 4k and 8k but
   is fine at 6k, 7k, 9k and 12k. win8192 is flat (2.89-3.00) across
   all nine. Across-content CV: **win128 12.4%, win512 8.6%, win8192
   1.3%.** No length-monotone mechanism produces that shape.
2. **Re-measuring the SAME cell on different documents removes the
   dip.** At ctx=8000, identical stack and window, only the C4
   documents changed: tau goes 2.239 -> 2.891 -> 2.963 (+29%, +32%).
   The quant-only single measured on those same documents does not
   move (2.846 / 2.863 / 2.875).
3. **Batching averages it away.** b1 uses ONE document (the loader
   tiles `docs[0]` to the batch size); b8 uses 8 and b32 uses 16.
   dense win512 at 8k: 2.239 (b1) -> 2.805 (b8) -> 2.861 (b32); llama
   2.091 -> 2.740 -> 2.767.

**Mechanism.** Prompt packs are nested -- the 8k pack is a strict
prefix of the 14k pack -- so each context length truncates the same C4
stream at a different point and hands the draft a different tail. With
the full window the draft sees all of it and acceptance is
content-flat; with a 512-token window acceptance depends on whether
that particular tail is locally predictable. The 8k tail lands inside
a gemstone-glossary catalog whose format is established thousands of
tokens earlier. Both architectures dipped together because they share
the input, not because they share a mechanism.

**Consequence -- the cell flips.** Re-measuring the composition itself
on fresh documents at b1/c8000, K=2:

| arch | sample | tau_comp | S_comp | S_single | winner |
|---|---|---|---|---|---|
| dense | original | 2.239 | 1.024 | 1.209 | single |
| dense | docs +16 | 2.840 | 1.270 | 1.209 | **composition** |
| dense | docs +32 | 2.839 | 1.295 | 1.209 | **composition** |
| llama | original | 2.192 | 0.941 | 1.192 | single |
| llama | docs +16 | 2.839 | 1.223 | 1.192 | **composition** |
| llama | docs +32 | 2.565 | 1.202 | 1.192 | **composition** |

On two of three draws per architecture the composition wins b1/8k, so
the reported loss at that cell was the unlucky draw, not a finding.
The b1/2k result above is unaffected: it involves no acceptance change
at all (tau 2.857 -> 2.857) and is a pure cost result.

**Exposure is bounded and now closed.** Sweeping every arm x batch in
the C1 grid for across-context spread, only win128 and win512 at b1
show it (CV 12.8-16.1%, collapsing to 1.8-4.6% at b8); every quant,
skip, kv-quant and wide-window arm sits at 0.3-5.7%. That is exactly
**4 exposed cells**, all re-measured on 3 document draws:

| cell | draw0 | +16 | +32 | mean | draw0 error |
|---|---|---|---|---|---|
| dense/win128 | 2.120 | 2.353 | 2.607 | 2.360 | -10.2% |
| dense/win512 | 2.239 | 2.891 | 2.963 | 2.698 | -17.0% |
| llama/win128 | 2.064 | 2.789 | 2.741 | 2.531 | -18.5% |
| llama/win512 | 2.091 | 2.789 | 2.789 | 2.556 | -18.2% |

**Protocol rule adopted:** at b1 a cell is one document, so any
content-sensitive arm needs >=3 document draws there. Content-
insensitive arms do not -- their across-content CV is ~1-3%.

**This is also a result, not only hygiene.** Narrow-window drafts have
an order of magnitude more acceptance variance across documents than
quantized drafts (CV 12.4% vs ~1%) at equal mean. A deployment picking
levers on a single-stream workload can draw a bad document and lose
20% of its speedup, with no such risk from quantization. Variance, not
just mean acceptance, distinguishes the levers.

### full-space demonstration (Step 3b)

The reduced oracle (18 configs) is too small to show the search's
saving -- 6 of its configs are singles the search must measure anyway.
Run the SAME search on the full dense space: quant{none,6} x
window{none,4} x skip{none,2} = 105 lever-combos x K{2,3,4,6} = **420
(config,K) boots exhaustive**.

| space | configs | exhaustive | search cost |
|---|---|---|---|
| reduced oracle | 18 | 36 boots | 16-22 (44-61%) |
| **full space** | **105 combos x 4 K** | **420 boots** | **27 confirmations (6.5%)** |

All 12 singles are REUSED from C1 Stage A -- same protocol, stack and
machine -- because acceptance is cell-independent and cost is measured
per single, not per composition. Charging the singles as if new still
gives 15.1%. **The space grew 12x; the search cost grew 1.4x.** That
is the O(#levers + #confirmations) claim, measured on both sides.

**Did the larger space pay?** Comparing the search's confirmed picks
against the reduced oracle's exhaustive optimum:

| regime | cells | mean gain over the reduced-oracle optimum |
|---|---|---|
| composition-LIVE (b>=8 & ctx>=8k) | 3 | **+4.1%** (peak +6.6%) |
| composition-DEAD (b1 or 2k ctx) | 5 | -1.7% |
| ungated, all cells | 8 | +0.5% |
| **with the Stage-0 cell gate** | 8 | **+1.5%** |

Honest reading: a fixed confirmation budget spread over a 12x larger
space is spread THINNER, so where the small space already held the
answer the wider search sometimes misses it (-1 to -3%). Where the
larger space genuinely contains better configurations it wins clearly
(+5.0%, +6.6%). This is exactly what Stage 0 (cell gating) exists for
-- gate on the measured two-binding-terms law and the wider search is
spent only where it pays, converting a +0.5% wash into +1.5% overall
and +4.1% on the live cells, at zero extra cost on the dead ones.

Caveat: 4 of the 27 confirmations (all Humming at K2 = verify width 3)
are blocked by the odd-width kernel wedge from the C1 ledger; the
affected cells use the search's next-best confirmed pick, so the
full-space numbers are a LOWER bound.


### reconciliation: pooled vs per-cell acceptance (a design refinement)

Two implementations of the same rule disagreed -- dense confirm-5
gave 2.58% regret with a POOLED acceptance profile and 0.46% with the
cell's OWN measured acceptance. The difference is real and instructive:
acceptance is cell-independent ENOUGH to profile once (CV 2.2-3.3%),
but that residual variation is INFORMATIVE, not noise -- using the
cell-local value is worth ~2 points of regret.

Crucially it costs nothing: Stage A already boots each single AT each
cell to measure R, and the same boot yields that cell's acceptance. So
the deployed rule is:
  * use the cell's own measured acceptance when the cell has been
    probed (free, better);
  * fall back to the pooled per-depth profile only for cells not yet
    probed (cold start / transfer).
Reported figures use the per-cell form: dense 0.46%, llama 0.00% at
confirm-5.

### status / gaps

- Regret is measured within the REDUCED oracle space; the full-space
  claim is a scaling extrapolation until Step 3 runs.
- Dense retains 0.46% regret at top-5 while llama reaches 0.00% —
  consistent with P3: dense's cost interactions are larger (skip's
  cost effect varies 67% by what it joins, and can flip sign), so
  Stage-A ranking is noisier there.
- kv-quant is excluded from the oracle (it requires dropping shared-KV
  = a different serving stack).
- MoE/MLA have no composition oracle; C1 showed them OFF-dominant, so
  composition there is expected to be moot but is untested.
